# Step 2.1a — The migration and Dexie version 3

**Branch:** `feat/phase-2-workout-log` · **Size:** M · **Depends on:** Phase 1
**Unlocks:** 2.1b, 2.2a · **Skill to load:** `db-migration`

The local store and the remote store must never drift. The SQL and the Dexie bump
land in this one step.

## Context to read first

1. `.claude/skills/db-migration/SKILL.md` — load it first.
2. `docs/specs/2026-09-20-gym-tracker-design.md`, section 5, the data model.
3. `supabase/migrations/` — the 2 Phase 1 migrations show the naming and the policy
   style.
4. `lib/db/dexie.ts` — `DATABASE_VERSION` is 2. Version 2 holds `deadLetters`.
5. The memory note on Supabase: apply migrations through the Supabase MCP tools.

## State before the step

The database has `profiles` and `daily_entries`. Dexie is at version 2.

## Goal

The 3 workout tables exist on the server and on the device, with Row Level Security,
and every Phase 1 row survives the upgrade.

## Do

1. Write `supabase/migrations/<YYYYMMDDHHMMSS>_phase2_workouts.sql`:
   - `exercises`, `workout_sessions` and `workout_sets` as the specification states.
   - Add `created_at` and `deleted_at` to all 3 tables, as the skill requires.
   - `exercises.user_id` may be null. A null row is a global seed row.
   - `exercises` policy: select where `user_id = auth.uid()` **or** `user_id is null`.
     Insert, update and delete only where `user_id = auth.uid()`.
   - `workout_sets` policy: an `exists` clause on the parent `workout_sessions` row
     with `user_id = auth.uid()`. The specification gives the table no `user_id`.
     Record this as a named exception in the migration header.
   - A partial unique index on `workout_sessions(user_id)` where
     `status = 'active' and deleted_at is null`.
   - Indexes on `workout_sets(session_id)` and `workout_sessions(user_id, entry_date)`.
   - Two new `profiles` columns: `rest_sound_muted boolean not null default false`
     and `rest_seconds_by_exercise jsonb not null default '{}'`.
2. Apply the migration through the Supabase MCP tools. Regenerate the types in
   `lib/supabase/`.
3. Bump `DATABASE_VERSION` to 3. Add `exercises`, `workoutSessions` and `workoutSets`
   to `STORES`. Index what a screen filters by: `muscle_group`, `session_id`,
   `entry_date`, `status`. Never change the version 1 or version 2 block.
4. Add the row interfaces to `lib/db/dexie.ts`.

## Acceptance criteria

- [ ] The migration applies on a fresh database with no error.
- [ ] Account A cannot read a session or a set of account B.
- [ ] Account A reads a row with `user_id is null`, but cannot update it.
- [ ] A second active session for one user is refused by the server.
- [ ] A Dexie database at version 2, with daily entries, a profile and a dead letter,
      opens at version 3 with every row kept.
- [ ] `DATABASE_VERSION` is 3.

## Tests

- Unit: open a version 2 database with real rows, then open it with the version 3
  code. Every row is still there.
- By hand, through the MCP SQL tool: the 3 policy checks above, with 2 test users.

consider" section. Test the policies with 2 real users, not with the service role,
which skips Row Level Security.
