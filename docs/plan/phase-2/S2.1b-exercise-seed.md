# Step 2.1b — The global exercise seed

**Branch:** `feat/phase-2-workout-log` · **Size:** S · **Depends on:** 2.1a
**Unlocks:** 2.2c

The picker needs a list on the first day. This step adds data only. It changes no
table, so it needs no Dexie bump.

## Context to read first

1. `supabase/migrations/<timestamp>_phase2_workouts.sql` from step 2.1a.
2. `docs/specs/2026-09-20-gym-tracker-design.md`, section 5 — the 7 muscle groups.

## State before the step

The `exercises` table exists and is empty.

## Goal

About 40 global exercises exist on the server, with fixed ids, across all 7 muscle
groups.

## Do

1. Write `supabase/migrations/<YYYYMMDDHHMMSS>_phase2_exercise_seed.sql`.
2. Insert about 40 rows with `user_id = null`. Cover chest, back, legs, shoulders,
   arms, core and cardio.
3. Give each row a fixed UUID in the SQL. A fixed id keeps the seed the same on every
   database. Phase 3 reuses these ids.
4. Keep the names plain: `Bench Press`, `Lat Pulldown`, `Leg Press`.
5. Use `on conflict (id) do nothing`, so a rerun adds no duplicate.
6. Apply the migration through the Supabase MCP tools.

## Acceptance criteria

- [ ] Every one of the 7 muscle groups has at least 3 exercises.
- [ ] No 2 seed rows share a name.
- [ ] Every seed row has `user_id is null` and a fixed id.
- [ ] A rerun of the migration adds no row.

## Tests

By hand, through the MCP SQL tool: count the rows per muscle group and check the
names for duplicates.

## Verification

1. The 4 checks above.
2. `pnpm verify`.

## Files touched

- `supabase/migrations/<timestamp>_phase2_exercise_seed.sql`

## Risk

A seed id that changes later breaks every set that points to it. Treat the ids as
permanent.

## When the step is done

1. `pnpm verify`
2. The `commit-report` skill.
3. Commit `feat(db): seed the global exercise list`
4. Set **Next step** in `PROGRESS.md` to `2.2a`.
