# Step 3.3 — The coach exercises and the plan column

**Branch:** `feat/phase-3-coach-plans` · **Size:** M · **Depends on:** 3.2
**Unlocks:** 3.6 · **Skills to load:** `db-migration` · **Agent to use:** `sync-auditor`

## Context to read first

1. `.claude/skills/db-migration/` — load it first.
2. `.claude/rules/architecture.md`, the UUID rule and the owner column.
3. The Phase 2 migration and its exercise seed in `supabase/migrations/`.
4. `lib/db/dexie.ts`. Read `DATABASE_VERSION`. Do not trust a number in a plan file.
5. `lib/plans/coach.ts` from step 3.2.

## State before the step

The seed has about 40 global exercises from Phase 2. Some coach exercises are there,
for example `Lat Pulldown` and `Leg Press`. Others are not. `workout_sessions` has no
plan column.

## Goal

Every coach step points at a real exercise row, and a session can say which plans it
runs.

## Do

1. List the 26 coach names against the Phase 2 seed. Match on the name, case
   insensitive.
2. For a match, put the seed row's UUID into `lib/plans/coach.ts`. For no match, keep
   the step 3.2 UUID.
3. Write one timestamped migration, through the `db-migration` skill:
   - Insert every coach exercise with no match as a global row: `user_id` null, the
     fixed UUID, the name and the muscle group.
   - Use `on conflict (id) do nothing`, so the migration runs twice with no error.
   - Add `workout_sessions.plan_ids text[] null`.
   - A check that every element of `plan_ids` is 1 of the 4 plan ids.
4. Bump Dexie by 1 from the live `DATABASE_VERSION`:
   - Add the local table `planCursors`, keyed on `sessionId`.
   - Write the upgrade function. Never drop a table.
5. Add `plan_ids` to the Phase 2 session schema in `lib/schema/`: an array of
   `PlanId`, nullable, default null.
6. Add `planCursors` to `.claude/rules/architecture.md` as local device state, next to
   `syncMeta`. It is not an entity and carries no outbox entry.
7. Regenerate the Supabase types with `pnpm types:db`.

## Acceptance criteria

- [ ] Every `exerciseId` in `lib/plans/coach.ts` exists in the seed after the
      migration.
- [ ] No coach exercise is a second row with the same name as a seed row.
- [ ] The migration runs twice on the same database with no error.
- [ ] A `plan_ids` value of `{'chest-triceps','foo'}` fails the check.
- [ ] The Dexie upgrade keeps every row of every older table.
- [ ] A session with `plan_ids: null` still parses, so every Phase 2 session stays
      valid.

## Tests

- `lib/plans/coach.test.ts`: read the migration and the Phase 2 seed as text. Assert
  every `exerciseId` appears in one of them.
- `lib/db/dexie.test.ts`: open the old version with rows, upgrade, assert the rows.
- The session schema test: `plan_ids` null, 1 id, 2 ids, and 1 unknown id.

## Test by hand

Apply the migration through the Supabase MCP. Run it again. Insert a session with a
bad plan id in the SQL editor, and see the check reject it.
