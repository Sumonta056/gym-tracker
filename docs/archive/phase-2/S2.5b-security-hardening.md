# Step 2.5b — Security hardening

**Branch:** `feat/phase-2-workout-log` · **Size:** M · **Depends on:** 2.5
**Unlocks:** 2.6 · **Agents to use:** `sync-auditor` (part A), `test-writer`

The `vibe-security` audit on 2026-09-30 found 2 medium issues and 3 low issues. It found
no critical or high issue. RLS is on for all 5 tables, with 4 policies each. No secret is
in the client bundle or in the git history. This step closes the 5 issues.

The step has 4 parts. Parts A, B and C are code. Each part is one commit, with its own
`pnpm verify` and its own report. Part D is the owner's work in the Supabase dashboard.

## State before the step

| #   | Level  | Where                    | Issue                                                                                                                                            |
| --- | ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Medium | `app/sw.ts:20-26`        | The service worker keeps every Supabase `GET` response in the `supabase` cache. `clearAll` does not delete it. Health data stays after sign-out. |
| 2   | Medium | `lib/auth/actions.ts:34` | `signInWithOtp` creates a user for an unknown email. A stranger can make an account on a one-user app.                                           |
| 3   | Low    | `lib/auth/actions.ts:26` | The magic-link redirect comes from the `Origin` request header. A wide redirect allow list lets an attacker receive the login code.              |
| 4   | Low    | `next.config.ts`         | The app sends no security header. Another site can put the app in a frame.                                                                       |
| 5   | Low    | Supabase Auth            | Leaked password protection is off. The local minimum password length is 6.                                                                       |

Issue 1 in detail: the cache key is the URL only. After a sign-out the pull cursor resets,
so the next account sends the same pull URL. On a slow network (more than 10 s) or with
no network, `NetworkFirst` returns the old account's rows to the new account.

## Goal

- No Supabase response is kept in the Cache Storage of the browser.
- Only an existing account can get a magic link. The reply does not tell whether an
  email has an account.
- The magic-link redirect is a fixed URL that the request cannot change.
- Every page sends 5 security headers.
- The Supabase dashboard refuses sign-ups and weak passwords.

## Decisions

1. **Remove the Supabase cache. Do not clear it at sign-out.** Dexie is the offline store.
   The cache adds no offline value, and a stale pull response can confuse the sync. A
   `NetworkOnly` rule stops `defaultCache` from a match on the Supabase host.
2. **Delete the old cache in the `activate` event.** Devices that run the old service
   worker keep a `supabase` cache. The new worker deletes it one time.
3. **The redirect reads `SITE_URL`, a server-only variable.** It has no `NEXT_PUBLIC_`
   prefix, because only the server action reads it. With no `SITE_URL`, the action omits
   `emailRedirectTo` and Supabase uses the Site URL in its dashboard.
4. **An unknown email reads as sent.** With `shouldCreateUser: false`, Supabase refuses an
   unknown email. The action maps that one refusal to `{ status: 'sent' }`, so the screen
   shows the same text for a known and an unknown email. Any other error stays
   `SEND_FAILED`. Confirm the exact error code in the Supabase docs (Context7) before you
   write the test.
5. **No full Content Security Policy in this step.** The Next.js inline scripts need a
   nonce from the middleware. That is a larger change with a risk to the service worker.
   This step sends `frame-ancestors 'none'` only.

### Part A — The service worker cache · `fix(pwa)`

1. Write the e2e test first, in `tests/e2e/security.spec.ts`:
   - Sign in, save a day, wait for the chip to turn green.
   - Read `caches.keys()` and every request in every cache.

### Part B — The magic link · `fix(auth)`

1. Write the unit tests first, in `lib/auth/actions.test.ts`:
   - `it('never creates a user for an unknown email')` — the call carries
     `shouldCreateUser: false`.
   - `it('reports sent for an email with no account')` — the Supabase refusal for an
     unknown email returns `{ status: 'sent', email }`.
   - `it('still reports an error for any other failure')`.
   - `it('builds the redirect from SITE_URL, never from the origin header')` — set the
     `Origin` header to `https://evil.example`. Expect `${SITE_URL}/auth/callback`.
   - `it('omits the redirect when SITE_URL is not set')`.
   - `it('omits the redirect when SITE_URL is not a valid URL')`.
2. In `lib/auth/actions.ts`:
   - Read `process.env.SITE_URL`. Parse it with `new URL(...)` and keep `.origin`.
   - Pass `{ shouldCreateUser: false, emailRedirectTo }` to `signInWithOtp`.
   - Remove the `headers` import from `next/headers`.
3. Add `SITE_URL=` to `.env.example`. Add `SITE_URL=http://localhost:3000` to `.env.local`.
4. Add `SITE_URL` to the CI build env in `.github/workflows/ci.yml`, if the e2e job sends
   a magic link. If no e2e test sends one, leave CI as it is.

### Part C — The security headers · `fix(setup)`

1. Write the e2e test first, in `tests/e2e/security.spec.ts`. Request `/sign-in` and `/`.
   Expect these 5 headers on each response:

   | Header                    | Value                                      |
   | ------------------------- | ------------------------------------------ |
   | `Content-Security-Policy` | `frame-ancestors 'none'`                   |
   | `X-Frame-Options`         | `DENY`                                     |
   | `X-Content-Type-Options`  | `nosniff`                                  |
   | `Referrer-Policy`         | `strict-origin-when-cross-origin`          |
   | `Permissions-Policy`      | `camera=(), microphone=(), geolocation=()` |

2. In `next.config.ts`, add an `async headers()` that returns the 5 headers for
   `source: '/:path*'`.
3. Confirm `/sw.js` and `/manifest.webmanifest` still load. Run the Lighthouse PWA check.

### Part D — The Supabase dashboard · the owner

These settings are not in the MCP tools. The owner sets them by hand. The agent only
lists them in the report.

1. Authentication → Sign In / Providers → turn off **Allow new users to sign up**.
2. Authentication → URL Configuration:
   - **Site URL** is the production URL.
   - **Redirect URLs** hold exact entries only: `https://<production>/auth/callback` and
     `http://localhost:3000/auth/callback`. Remove every wildcard, for example
     `https://*.vercel.app/**`.
3. Authentication → Password security:
   - Minimum length 8 or more.
   - Turn on **Leaked password protection**. This needs the Pro plan. On the Free plan,
     record it as an accepted risk in the report.
4. Vercel → the project → Environment Variables → add `SITE_URL` for Production.
5. In `supabase/config.toml`, set `enable_signup = false` in `[auth]` and `[auth.email]`,
   and `minimum_password_length = 8`. This is for the local stack only. It goes in the
   part B commit.
6. After the changes, run `get_advisors` for security. Report any warning that is left.

## Risk

- **Part A:** a wrong matcher lets `defaultCache` cache Supabase again, or stops the pull.
  The e2e check and `offline.spec.ts` catch both.
- **Part B:** the password sign-in is the default and does not change. The magic link is the
  fallback. If `SITE_URL` is wrong on Vercel, the link lands on a wrong host. Test one real
  link on production after the deploy.
- **Part C:** `X-Frame-Options: DENY` blocks the app in any frame. The app has no frame use
  today.
- **Part D:** with sign-ups off, the E2E account must already exist. It does. No test calls
  `signUp`.

## Not in scope

- A full Content Security Policy with a nonce. Decision 5 gives the reason.
- Rate limits of our own. Supabase Auth already limits sign-in and email per IP.
