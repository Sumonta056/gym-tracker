# Step 1.5 — Shared zod schemas

**Branch:** `feat/phase-1-daily-tracker` · **Size:** S · **Depends on:** 1.4
**Unlocks:** 1.6

## Context to read first

1. `.claude/rules/architecture.md`, the "Shapes" section. One schema per entity.
   Never re-declare a shape.
2. `lib/supabase/database.types.ts` from step 1.2. The schema must match it.
3. `lib/duration.ts` from step 1.4. Durations are integer seconds.

## State before the step

`zod` is not installed. There is no `lib/schema/` folder.

## Goal

One zod schema per entity. The form, the outbox and the CSV importer all import from
here.

## Do

1. Install `zod`.
2. Write `lib/schema/dailyEntry.ts` with these bounds:
   - `avg_heart_rate` and `max_heart_rate` between 30 and 230.
   - `max_heart_rate` is at least `avg_heart_rate`. Use a refinement.
   - `weight_kg` between 20 and 300, two decimals.
   - `calories_burnt` between 0 and 10000.
   - `steps` between 0 and 200000.
   - `entry_date` is an ISO date and is not in the future.
   - `walk_seconds` and `gym_seconds` are non-negative integers.
   - `note` is optional text.
3. Write `lib/schema/profile.ts`.
4. Export the inferred types, for example `DailyEntryInput`.

## Acceptance criteria

- [ ] Each numeric bound has two tests, one above and one below the limit.
- [ ] A `max_heart_rate` below `avg_heart_rate` fails the refinement.
- [ ] A `max_heart_rate` equal to `avg_heart_rate` passes.
- [ ] Tomorrow as `entry_date` fails. Today passes.
- [ ] `weight_kg` with three decimals fails.
- [ ] The inferred type is assignable to the generated Supabase row type. Prove this
      with a type-level assertion in the test file.
- [ ] No other file declares a daily entry shape.
